# FlowPilot 面试追问与回答提纲

以下回答针对实际代码和2026-11-14联调。讲清已实现范围和改进方向，不把文档设计、Mock和真实生产混为一谈。

## 1. 60秒介绍项目

我基于营销与客服设计材料实现了一个前后端工作台，核心是营销任务从方案生成、人工审批、双臂试点到排重全量交付的闭环。后端使用FastAPI、SQLAlchemy和LangGraph，异步生成三套候选，数据库保存业务状态和事件，前端展示审批与交付过程。我接入DeepSeek Flash完成了15次真实调用和浏览器联调，并用23项离线测试覆盖并发、异常和契约。当前是单进程作品集工程，客服使用规则路由，没有真实投放或退款。

## 3. 后端并发与一致性

**为什么用asyncio？为什么还要Semaphore？**  
模型调用以网络等待为主，asyncio适合I/O并发；Semaphore约束单任务候选同时执行数，as_completed先处理完成者。当前不是全局并发限制，多活动会叠加，需要队列或共享容量控制。

**为什么不用gather？**  
gather默认等所有结果再统一处理，不利于尽早保存和展示候选。as_completed按完成顺序持久化，但仍要为每个分支处理异常。

**怎么防重复生成和重复审批？**  
使用SQL `UPDATE ... WHERE status=expected` 检查rowcount，只有一个请求能从预期阶段推进；失败返回409。不要先读取状态再无条件写入。

**导出为什么要锁，唯一键不够吗？**  
约束只能拒绝重复插入，不能让竞争请求都自然拿到同一结果；事务中先取得写锁再复查已有产物，以campaign+kind唯一键兜底。对象写入与数据库提交不是分布式事务，崩溃可能产生孤立文件。

**怎么保证exactly-once？**  
不声称跨系统exactly-once；当前是单进程状态恢复和幂等结果复用。外部副作用需要业务幂等键、outbox、重试及对账。

**服务重启从哪个节点继续？**  
启动时重跑GENERATING任务，并清理部分候选；不是LangGraph节点级Checkpoint。模型调用可能重复，预算日志保留已有请求预留。

**能开多个uvicorn worker吗？**  
不建议。没有任务租约及fencing，多个实例可同时恢复同一任务；预算文件锁也只在一个进程内生效。生产化要引入持久任务队列、认领和租约续期。

**慢存储是否阻塞事件循环？**  
写对象使用to_thread，但读取试点文件排重存在同步调用，尤其远端MinIO会阻塞；下一步改为异步适配或在线程中完成，避免持有数据库锁做慢网络I/O。

## 4. 模型契约、成本与安全

**JSON模式是否就能保证可用？**  
不能。还要检查finish_reason、非空字段、字段类型与长度、额外字段，以及业务语义。联调中拒绝说明结构正确，但不是可执行方案。

**为什么没有自动重试？**  
本次费用受限，选择显式失败隔离以方便核算。生产上仅重试可恢复的429/部分5xx，指数退避+jitter+最大次数；认证、参数、规则拒绝不应盲重试。

**超时是不是没花钱？**  
不是。客户端超时不等于供应商没有生成；未知usage按完整预留预算记账，不能以未收到响应推断免费。

**10元怎么控制？**  
输出600Token、输入字节上限、最多18次生成、调用前预算预留、返回usage后结算；按远高于所用模型价格的100元/百万Token记预算，未返回usage保留全部预留。此机制仅单进程有效，不是多租户计费系统。

**测试花了多少？**  
15次调用，5088Token；按官方Flash峰价测算0.00235344美元。本地保守预算占用0.5088元，二者都不是平台实际账单。不要用预算上界自称精确成本。

**你测到的成功率是多少？**  
这15次JSON契约均通过，但初始4场景12个候选中只有10个入库，另2个被规则拦截。样本少，不能推广为准确率或生产成功率。拒绝说明被保存为候选也属于业务语义缺口。

**怎样证明没有事实幻觉？**  
当前无法证明。提示只要求使用已知事实，仍需要把权益、日期、金额建模为输入事实并校验输出，结合人工审核；通顺的文案不是事实一致性的证据。

## 5. SSE、实验与数据

**SSE流的是模型Token吗？**  
不是。供应商当前使用非流式JSON响应，SSE发送持久化业务事件。不要把节点/候选进度描述成逐Token流式生成。

**SSE断线怎么办？**  
事件带递增ID，客户端可用Last-Event-ID续接。当前数据库轮询，无事件总线；重复事件要幂等消费。带共享令牌时前端改用轮询，避免原生EventSource无法设置Authorization的问题。

**为什么A/B两臂必须互斥？**  
避免同用户受到两套方案干扰。固定种子分配便于复现，全量阶段排除两臂已暴露客户；不只排除胜出臂。

**转化事件怎么去重？**  
event_id唯一，实验内customer_id唯一。相同event_id不同载荷要返回冲突；同用户重复事件只计一次。

**转化率更高为什么不自动晋级？**  
只计算描述性转化率，未实现观察窗口、显著性、功效分析及真实归因；小样本单次转化不能证明效果更好，因此人工决定。

**怎么保证查询不越权？**  
当前只使用合成数据，缺少账号和租户隔离；共享令牌不提供对象级权限。真实订单必须由认证主体注入user_id并在工具层过滤，不能相信用户或模型传来的任意ID。

## 6. 面试时避免的表述

- 不说“生产级多Agent平台”“高并发已验证”“节点级断点续跑”“客服大模型工具调用已落地”。
- 不把23项测试称为23个真实业务场景，不把15次模型调用称为大规模评测。
- 不把SSE业务事件说成供应商Token流，不把规则评分说成模型评审。
- 不拿合成客户数量说明真实使用规模，不拿模拟转化说明营销收益。
- 可以明确说“我在真实联调里发现并记录了语义契约和护栏误报问题，并能解释下一步如何修复”。

## 7. 最值得独立补的三项

1. 结构化产物类型+澄清状态：解决真实测试已暴露的语义错误，比继续增加框架名更有价值。
2. 全局任务队列+租约：解决跨campaign并发及多进程恢复竞态。
3. 固定评测集：分别测字段契约、事实一致性、规则误报/漏报、业务状态，不把它们合成一个漂亮但无意义的准确率。

## 多进程更新

当前53项回归；同机3服务进程及8预算竞争进程通过验证。已新增SQL租约、owner写入校验、续期和自动接管。可解释为什么这是“防止旧owner提交”，而不是外部模型调用exactly-once；MODEL_CONCURRENCY仍每worker有效，文件费用锁依赖同机共享路径。详见多进程验证报告。
