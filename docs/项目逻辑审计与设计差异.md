# FlowPilot 项目逻辑审计与设计差异

审计日期：2026-11-16。范围：营销与客服原始设计材料的本地文字提取、当前 app/、web/、tests/、scripts/、README 与 docs/。原始材料未上传仓库。本报告是代码走查与列明场景验证，不能等同于所有输入和部署环境均无缺陷。

## 结论

当前项目是一套可运行的运营工作流原型：真实 Python API、SQL 状态、LangGraph 文案生成、人工决策、实验分臂、CSV 名单、规则客服和独立政策检索已经形成闭环。公开 Pages 是浏览器模拟，不执行 Python 或真实模型。

原设计的复杂营销规划、多轮客服工具调用、行业包、画像圈选和节点级恢复尚未完整复现。最成熟的部分是流程约束、幂等交付、故障恢复与成本控制；最薄弱的部分是方案业务语义、策略生成和实际效果评估。

## 业务链路与代码证据

| 链路 | 当前实现 | 关键边界 |
|---|---|---|
| 创建与生成 | routes.py 创建 Campaign，SQL 条件更新进入 GENERATING，后台任务调用 marketing_graph | 创建和启动是两次请求；启动失败会留下 CREATED 任务，页面暂无对既有任务重新启动按钮 |
| 多候选 | campaigns.py 三分支、单任务 Semaphore(2)、进程级模型许可、as_completed、失败隔离 | 重跑会删除部分候选再重新调用模型；不是节点级继续执行 |
| 单方案 | approve 验证候选归属与实验冲突，PILOT_READY → PILOT_EXPORTED → COMPLETED | 试点仅表示名单已导出，不代表真实触达或效果验收 |
| A/B | experiments.py 固定种子互斥分臂，事件 ID/用户去重，人工晋级 | 没有自动观察窗口、显著性、推荐胜出者；前端固定取前两个候选 |
| 名单交付 | consent 过滤、分群、试点/双臂排重、产物唯一键、下载哈希检查 | CSV 只有 customer_id/segment/region，未包含文案绑定、触达执行或外部投放回执 |
| 执行恢复 | leases.py owner 校验、续期和过期接管；main.py 定期扫描 | 依赖同机时间及共享路径；外部模型可能重复收费 |
| 客服 | support.py 规则分流、服务器生成会话 ID、SQL 历史、待确认保护 | 没有客服 LangGraph、多轮 LLM tool-use、真实订单/工单/退款 |
| 政策知识库 | knowledge.py Markdown 分块、中文 bigram BM25、来源引用、空结果拒答 | 独立只读入口；模型只选择片段 ID，回答仍为原文摘录；客服聊天未自动接入此检索 |
| 模型成本 | provider.py 结构化输出、超时、响应体上限；budget.py 文件锁预留/结算 | 费率是预算保护参数，不是供应商实际账单；无跨主机全局预算 |

## 与原始技术设计的逐项差异

| 原设计要求 | 当前状态 | 差异及影响 |
|---|---|---|
| Plan/Pilot/Full 跨请求生命周期 | 部分实现 | Campaign 状态保留主要阶段，没有完整 PlanPhase、plan revision、运营修订及独立交付运行快照 |
| 目标理解 → 人群 → 策略 → 文案 → 合规 → 置信度 | 简化实现 | 三节点中 Planner 只写预算/人群理由，Executor 生成文案，Critic 按长度和编号评分；没有真正的策略规划及置信度估计 |
| 信息不足转 NEEDS_CLARIFICATION | 未实现 | 通过长度校验即可生成；无法用任务状态要求补齐权益、渠道或观察目标 |
| 合规 BLOCK 与定向重试 | 部分实现 | 固定预算阈值和三个禁用短语检查，没有完整 PII/事实一致性/时段规则，没有合规修订回路 |
| 预算影响方案 | 未实现生成约束 | budget 存在 SQL 和 Planner 输入中，但 Executor 调用 draft 只传 brief/audience/variant；真实模型请求不含 budget |
| 各候选独立 thread_id/checkpointer | 未实现 | 独立输入与并发隔离已存在，图以 compile() 无 checkpointer 构建；恢复重跑整次任务 |
| Segment DSL、TagCatalog、ClickHouse 估算及拉取 | 未实现 | 只按四种枚举客群查询合成 Customer；不能执行复杂画像规则 |
| DSL 多样性与候选差异化 | 未实现 | Mock 三种角度；真实模型只有 variant 参数，没有 DSL Jaccard、多样性评估或 A/B 策略约束 |
| pilot_ratio、window_days、回流实验结论 | 部分实现 | 单方案最多25人、实验默认每臂10人；没有可配置观察窗口、自动结论或统计检验 |
| winner 快照 + 运营 edits + full 发布 | 部分实现 | 选中候选并排重导出；不执行修订、发布、触达、回执 |
| 客服完整节点图与意图/实体抽取 | 未实现 | 当前为关键词路由；不做模型抽取、结构化实体补齐或完整节点编排 |
| 简单查询/复杂多轮 tool_use | 未实现 | 订单是占位事实，政策是固定事实；独立 BM25 知识库不能代替工具调用编排 |
| IndustryPack 六注入点 | 未实现 | FAQ 和规则写在代码中；没有可替换行业包协议 |
| 七算子规则决策 | 仅辅助函数 | evaluate 有函数和单元测试，app 业务链路没有调用；不能说已驱动客服或营销决策 |
| 高风险操作由规则与用户确认控制 | 核心语义已实现 | 明确确认才记录审核状态，但没有外部业务动作；未知请求也未统一进入设计要求的安全确认分支 |
| SSE 阶段轨迹 | 营销部分实现 | 营销为数据库事件流；客服是普通 HTTP 请求，无逐节点 SSE 或模型 Token 流 |

原始客服材料同时含“手写调度、不引入 LangGraph”和“改为 LangGraph”修订文字；应先明确目标版本。无论采用哪种调度，当前客服均未实现该完整节点图。

## 仍需处理的逻辑问题（按优先级）

1. **P1：结构合法不等于可执行方案。** provider 只要求 title/message/reasoning，拒绝说明仍可能通过并被审批；缺少 draft/clarification/refusal 分类。应先补类型和状态，再决定是否允许导出。现有评分不能用于自动决策。
2. **P1：预算没有进入生成请求。** 模型无法按预算规划，当前阈值检查也没有估算费用、补贴或触达成本。当前文档已收敛为“固定预算阈值校验”。
3. **P1：实验恢复依赖标签页 sessionStorage。** 后端实验是真实持久化的，但前端仅用 exp-{campaign_id} 找回；清除该键或换新标签页后选择旧实验任务，看不到实验区，普通审批按钮也可能重新可点（后端仍以409拦截）。需要以服务端 experiment_id 或按 campaign 查询恢复，不应把浏览器缓存当业务真源。
4. **P1：待确认客服操作刷新后缺少按钮恢复。** history 只渲染消息，页面刷新后 confirmBox 不从后端会话状态还原；可继续发送“确认/取消”处理，但按钮不一致。应提供会话状态读取并恢复按钮。
5. **P2：创建/启动失败后的继续入口缺失。** create 成功但 generate 返回429/网络失败后，历史中的 CREATED 任务缺少继续生成按钮，用户只能另建任务。
6. **P2：演示反馈只代表一个用户。** 按钮总是提交 arm.users[0] 与固定 event_id，多次点击仍是一次转化。这验证去重，但不适合演示多个用户的回流趋势。UI应明确“一名用户，重复点击验证去重”，另加选用户入口。
7. **P2：在线模拟与后端样本映射不同。** demo.js 的500人 segment/region 索引与 main.py 种子相差1；同一客户 ID 所属分群不同。两者目前没有承诺数据一致，但不能用于逐 ID 对账。
8. **P2：交付证据展示不足。** API/数据库有 SHA256，页面产物按钮只展示类型和行数；前端没有完整哈希、试点排重计数、双臂重叠数和选中方案绑定的解释视图。
9. **P2：政策检索缺少语义相关性评测。** BM25 只要有词匹配就可返回；没有检索阈值/重排或业务评测集，不能由“有引用”推导“答对问题”。
10. **P2：生产运行条件缺失。** 无租户与对象权限、数据库迁移、跨主机预算、真实触达及工单接口；PostgreSQL/Redis/MinIO 组合仍须独立实测。

本次不把上述问题全部改造成新功能；它们是代码走查确认的后续工作。已修复的发布问题是仓库改名后的地址、过时单进程限制，以及用户指南和当前页面布局不一致。

## 文档一致性修正

- 仓库已由 temp 改名为 FlowPilot；本次同步受版本控制的仓库、Pages、徽章和克隆链接。
- 设计映射文档原来仍写“必须单进程”，与当前租约实现矛盾；已改为共享存储下的同机多进程。
- DeepSeek 早期报告的调用数、剩余额度和锁边界为历史快照，补充历史标记，不把当时数据作为当前预算承诺。
- 用户指南改为顶部四工作区入口；README 明确预算为固定阈值、哈希由 API 提供。
- 早期验收的64项和模型联调的23项是当时测试快照；当前回归为78项，不能简单相加或视为测试数量倒退。

## 已经具备的实际价值

- **可演示的业务闭环**：从目标到候选、审批、试点、全量产物，能够用于项目讲解、流程评审和前后端协作；比单轮聊天更能体现业务状态与操作约束。
- **可检验的后端能力**：SQL 条件更新、并发隔离、事件去重、产物幂等和哈希校验都有具体实现及测试，能围绕竞态、重复请求、断流和崩溃恢复讨论工程选择。
- **可控制的模型接入**：模型密钥留在后端，有输出契约、调用上限和费用预留机制，便于低成本继续研究；未验证所有供应商及所有模型业务质量。
- **可复用的流程骨架**：状态机、产物交付、人工确认和政策检索可作为下一阶段真实业务适配基础；仍需接入身份、数据源和审计。
- **求职展示价值**：可以据实描述“独立实现营销与客服工作流原型，并验证本地闭环、并发幂等与同机恢复”；不能描述为已复刻完整企业系统、真实提升转化率或达到生产规模。

当前没有真实投放、客户反馈、人工节省工时或营收数据。因此业务收益只能提出待验证假设，不能给出转化提升或成本节约百分比。

## 建议推进顺序

先处理方案分类/澄清、预算传入、实验和客服状态恢复；再补文案事实评测与交付证据；随后接入一个真实但受控的数据源/业务工具，最后再考虑跨主机和复杂中间件。每一阶段应以可执行样例和反例验收，而非仅增加技术组件。

## 本轮验证记录

- 本地 pytest：78项通过，使用隔离存储与 Mock/故障传输。
- Edge 静态演示：场景填入、A/B 反馈晋级、单方案试点、CSV 下载、客服确认、四工作区手机布局通过；无 JS 异常，无后端或模型网络请求。
- PR #1 合并提交：00d953d4dfee86e0bf0d31c2893bea3e225720a6，远程 CI 和 Interactive demo 均成功。
- 本轮不调用付费模型；历史真实模型结果见单独报告。此次检查不能证明真实业务质量或外部基础设施组合可用。

- 本轮重跑同机多进程：三服务启动、租约续期、强杀接管通过，接管约1.64秒；60次生成/审批竞争各仅1次接受，60次导出同一产物；8进程竞争2次调用名额，2接受/6拒绝。
- 浏览器专门复现：删除 exp-* 标签页缓存后实验面板消失、普通审批被API拦截；待确认客服申请刷新后消息恢复、确认按钮未恢复。两项仍待修复。
